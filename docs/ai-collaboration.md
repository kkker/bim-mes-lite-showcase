# 與 Claude Code 的協作方式

本專案的程式碼大部分由 Claude Code（Anthropic 的 AI 程式助手）撰寫。我負責需求、技術決定、審查與提交；Claude Code 負責拆任務、實作與驗證。本文記錄這套分工的實際做法、為了讓它可控而加上的規則，以及過程中遇到的問題。

文中提到的檔案（`.claude/`、`tutor/` 等）都在私有的原始碼 repo，不在本 repo。

## 分工

| 角色 | 由誰擔任 | 負責 | 不做 |
|---|---|---|---|
| 需求與決定 | 我 | 撰寫規格、在衝突或取捨時做決定、確認無法自動化驗證的項目（3D 畫面） | — |
| 規劃者 | Claude Code 主對話（`/breakdown` 指令） | 依規格把一個階段切成小任務，寫出可驗證的驗收條件 | 不寫程式 |
| 協調者 | Claude Code 主對話（`/dispatch` 指令） | 分派任務給子代理、轉交驗證結果、追蹤進度 | 不直接改程式 |
| 實作者 | `implementer` 子代理 | 依單一任務修改程式與測試，交件前自行建置 | 不做任務範圍外的修改 |
| 驗證者 | `verifier` 子代理 | 讀 diff、在 Docker 中建置與測試、逐條比對驗收條件並附證據 | 不修改任何檔案 |
| 審查與提交 | 我（階段一～五）；階段六起由 Claude Code commit、我檢視 | 讀每個通過任務的 diff 並 commit；推送一律由我執行 | — |

子代理與指令以 Claude Code 的設定檔定義（`.claude/agents/`、`.claude/commands/`）。實作者與驗證者是兩個獨立的子代理，驗證者沒有編輯檔案的工具權限。

### 這套分工的由來（2026-11-13）

專案剛開始時，我找到 [Firstmate](https://github.com/kunchenguid/firstmate)（一個用來管理多個專案的 AI 代理工具），問 Claude Code 能不能裝進這個專案。Claude 評估後說明：

- Firstmate 本身是一個獨立的 repo，要放在專案外面，由它把專案 clone 進來，每個任務開一個獨立的 git worktree 與 tmux 視窗，交給其他代理執行。
- 需要另外安裝 tmux、GitHub CLI、終端機版的 Claude Code 與 worktree 工具；我當時用的是 VS Code 擴充套件。
- 我的 remote 是自架的 Git 伺服器，不是 GitHub，它自動開 PR 的流程用不了。

我的需求其實只有一個專案，重點是能讓多個任務經過「分派、驗證、回饋、再驗證」。把這個需求告訴 Claude 後，它建議直接用 Claude Code 內建的子代理：一個實作者、一個只讀不改的驗證者，再加一個串起整個循環的 `/dispatch` 指令。理由是：

- 不用另外安裝工具，也不受 remote 不是 GitHub 的影響。
- 設定檔跟著專案進 git，角色的每次修改都留有版本紀錄。
- 驗證標準可以依本專案的規格寫死，例如一律在 Docker 中建置、測試要全部通過。

它也列出其他選擇（Claude Code 實驗性的 agent teams、用 Agent SDK 自己寫流程、以平行執行為主的工具等）和不適合的原因，並註明第三方工具的資料沒有上網確認，可能已經過時。

我決定採用，並要求重點放在教我怎麼用。Claude 依規格建好兩個子代理、`/dispatch` 與 `/breakdown` 的範本，建議我先手動跑一次「分派 → 驗證 → 回饋 → 再驗證」，看懂每個角色的報告後再改用 `/dispatch` 一次跑完。它原本建議互不相關的任務可以在各自的 worktree 平行執行；我問到 8GB RAM 要怎麼協作後，改成子代理一律依序執行（見[給 AI 的環境限制](#給-ai-的環境限制)）。之後的文件體系、規則，以及協作模式的調整，都是在這個基礎上逐步加上的。

## 文件體系

子代理看不到主對話的內容，所以所有它們需要知道的事都寫成檔案，放在 `tutor/`：

| 檔案 | 內容 |
|---|---|
| `spec.md` | 需求規格：背景、技術棧、資料表、API、前端互動、測試策略、資安要求、各階段目標 |
| `decisions.md` | 仍有效的設計決定，包含規格沒寫明、或刻意與規格字面不同的地方，註明日期與來源任務 |
| `conventions.md` | 共通約定與共用指令（例如「後端 Docker 測試」的完整指令與通過判準），任務內文以簡稱引用 |
| `tasks.md` | 目前階段的任務、依賴關係、驗收條件 |
| `tasks-archive/` | 已完成階段的任務原文，只作歷史紀錄，不作驗收標準 |
| `security-notes.md` | 弱點掃描結果、防護與測試的對應、已知限制 |

文件衝突時的優先順序固定為 `spec.md` → `decisions.md` → 目前任務的驗收條件。發現衝突時，子代理不自行判斷哪邊優先：實作者停下來回報，驗證者判為不通過並標示「規格衝突」，由我決定，結果寫回 `decisions.md`。

## 一個任務的流程

```text
/breakdown 階段N
  └─ 規劃者讀 spec、decisions、conventions 與現有程式 → 寫入 tasks.md
我閱讀任務與驗收條件，必要時修改
/dispatch（或直接要求分派某個任務）
  ├─ implementer：實作 → 回報修改的檔案、自我建置結果、給驗證者的提示
  ├─ verifier：逐條驗收 → 通過／不通過＋問題清單（檔案:行號）
  ├─ 不通過 → 問題清單原文交回 implementer → 再驗證（附上一輪清單）
  └─ 同一任務最多 3 輪，仍不通過就停下來交給我
標示「使用者確認」的條件 → 我在瀏覽器操作確認
我讀 diff 並 commit（Claude Code 只建議 commit 訊息；階段六起改由 Claude Code commit，見下方「協作模式的調整」）
```

### 驗收條件的寫法

每條驗收條件都要寫得出「跑什麼指令、看什麼結果」，例如：

- 「後端 Docker 測試」全部通過，測試總數不少於任務開始前（回報前後數字）。
- `grep -rn "wwwroot" backend --include='*.cs' | grep -v Migrations` 沒有輸出。
- 「上傳範例模型」回 `HTTP 200`，構件數 149。
- 新增與修改的 `.cs` 檔為 CRLF（用 `file` 檢查）。

「程式碼品質良好」這類無法判斷的描述不寫進驗收條件。無法用指令驗證的項目（3D 渲染、點選、顏色）標示「使用者確認」，由我操作後才算通過。

從測試階段完成後，每個新任務的驗收條件都包含「相關測試已新增且全部通過」。

## 協作模式的調整：從逐任務到整個階段

**階段一～五：逐任務協作。**每個任務都由我下指令分派給實作者、再分派給驗證者。每一輪結果出來後，Claude Code 向我回報，我們確認溝通上的差異、協調處理方向，我確認驗證結果、讀 diff、自己 commit，然後才開始下一個任務。

**階段六起：整個階段交給 Claude Code 處理。**流程與規則（文件體系、驗收條件、實作者與驗證者分開）不變，改變的是我介入的時機：

- **開始前：**Claude Code 先列出這個階段可能需要我決定的問題，我一次回答。例如頻率限制怎麼計次、錯誤訊息的顯示方式、commit 的處理方式。
- **進行中：**Claude Code 自行依序分派、驗證、修正；遇到需要我決定的事仍會停下來詢問。階段六實際發生過三次：
  - 自動權限檢查擋下驗證者的「重置後端」，問我是否允許。我允許，但只限階段六。
  - 選到不合格檔案時畫面要怎麼處理（見下一節）。
  - 弱點掃描找到 1 個 High 等級的套件弱點，問修補方式。我選了升級 EF Core，另開任務處理。

  需要在瀏覽器確認畫面、或 Docker 需要重啟時，也會通知我。
- **commit：**每個任務通過後由 Claude Code commit（不推送），一個任務一個 commit，我在階段結束時用 Sourcetree 逐一檢視。推送到遠端與 registry 仍由我執行。
- **結束時：**Claude Code 交付每個任務的結果與注意事項，由我確認這個階段是否完成。

階段七沿用同樣的模式，目前進行中。到目前為止，還沒有出現需要大規模調整、影響整個階段的協調。

## 給 AI 的環境限制

開發機是 8GB RAM 的舊款 Intel Mac，無法安裝新版 .NET SDK 與 Node.js。這些限制寫在規格與約定中，作為所有子代理的前提：

- 禁止在本機執行 `dotnet`、`npm`，一律在 Docker 容器中執行。
- 同一時間只能有一個建置或測試容器；子代理一律依序執行，不平行。
- 推送映像檔到 registry 等對外動作，只由我執行。
- 帳號、密碼、token 不得出現在 repo 中。

## 過程中遇到的問題與調整

以下是實際發生、並因此加進規則的情況。

| 情況 | 調整 |
|---|---|
| 長時間使用後 Docker Desktop 明顯變慢（後端測試由約 25 秒變成 2～3.5 分鐘），調高逾時無法解決，重啟 Docker Desktop 後恢復 | 加入 Docker 健康檢查指令與門檻；超過門檻時停下來請我重啟 Docker，禁止以調高逾時或修改測試設定處理 |
| 3D 套件的 API 與 AI 記憶中的舊版不同 | 規定寫程式前先讀 `node_modules` 中實際安裝版本的型別定義 |
| 規格寫「先儲存再解析」，會讓壞檔留下孤兒檔案 | 改為先解析再儲存，記錄在 `decisions.md` 並註明與規格不同 |
| MinIO 官方映像檔已無法取得 | 該階段暫緩，保留儲存介面供日後替換 |
| 測試套件新版本要求較新的 Node，與當時的前端容器不相容 | 先用相容版本完成測試階段，另開任務升級 Node 映像檔 |
| `tasks.md` 隨階段累積過長，子代理每次都要讀入大量歷史內容 | 拆出 `conventions.md`、`decisions.md` 與 `tasks-archive/`，子代理只讀目前階段與相關決定 |

## 我的回應與 Claude 建議不同的地方

Claude Code 在規劃或回報時常會附上建議做法。以下整理我沒有照建議走、或在建議之外另加條件的情況，內容依對話紀錄整理。「原因」只列我當時有說明的部分。

### 不為刪除資料庫後的重建做自動重試（2026-11-15）
- **情境：**驗證前的「重置後端」會刪掉 SQLite 檔，後端在 Docker 掛載目錄重建資料庫時偶發失敗。
- **Claude 的建議：**新增一個任務，讓後端啟動時自動重試，驗收要求連續重置 3 次都不需要手動處理。
- **我的回應：**不做這個任務。
- **原因：**建立資料庫檔是專案初始化時的動作，不是日常流程，不需要為「停止 → 刪檔 → 啟動」這個流程做驗證。
- **結果：**該任務刪除；「重置後端」改為只清空資料表、不刪除資料庫檔。

### 等待迴圈加上次數上限（2026-11-16）
- **情境：**子代理用 `pgrep -f` 等待背景工作，因為比對到迴圈自己的指令列而一直不結束。
- **Claude 的建議：**在派工指示中交代「不要用會卡住的等待迴圈」。
- **我的回應：**改成具體規則：每個迴圈都要有計數器，上限遠大於預期次數（例如預期 10 次，上限設 9999）；結束時若計數到達上限，視為可能的無限迴圈，必須查明原因並修正。
- **原因：**這樣迴圈即使超過預期次數也一定會結束，而且到達上限本身就是需要檢查的訊號。
- **結果：**寫進共通約定，所有任務適用。

### 登入列為下一個階段，並在之後重做資安檢查（2026-11-17、2026-11-19）
- **Claude 的建議：**Demo 專案先不加登入，只做基本防護。
- **我的回應：**同意先做基本防護，但登入、使用者與權限要列為下一個目標。階段六結束後再補充：加入登入後，要再做一次資安基本防護。
- **原因：**加入登入後會多出新的存取方式（登入端點、帳號、角色）。
- **結果：**規格新增階段八，並註明完成後依第 11 節重新檢視。

### 不接受測試後要等 3～7 分鐘才能回到開發（2026-11-18）
- **情境：**跑完後端測試再啟動開發用的後端，要等 3～7 分鐘。
- **Claude 的建議：**說明原因是測試容器與服務容器的掛載路徑不同，造成重新還原與編譯，啟動時需要等待。
- **我的回應：**請它上網查有沒有能省掉重新編譯、又能共用建置結果的做法。
- **原因：**每次測試完回到開發都要等 5 分鐘左右，這樣的開發效率無法接受。
- **結果：**新增任務統一兩種容器的路徑。實測後發現，3～7 分鐘主要是 Docker 長時間運作後變慢造成的，重新還原只占約 3.5 秒；但服務與測試輪流執行時，仍有約 50 秒的重新編譯。

### 繼續追查 50 秒的重新編譯，並先查外部資料（2026-11-18）
- **Claude 的建議：**保留路徑統一的改動，修正文件說明即可。
- **我的回應：**保留改動，另開任務查清楚為什麼每次都重新編譯。
- **原因：**希望省下每次輪流執行時的這段時間。
- **後續：**原因查到後（測試容器看得到 `.git`，.NET 8 SDK 會把 commit 雜湊加進組件版本字串），Claude 建議方案 A（完全關閉 git 查詢）。我請它先上網找有沒有人遇過相同情況、推薦什麼解法。查到 Microsoft 官方文件的做法後，Claude 改為建議方案 B（只拿掉版本字串中的雜湊），我採用方案 B。

### 可調整的數值只改一處（2026-11-18）
- **情境：**規劃資安階段時，上傳上限 50MB、每分鐘 5 次上傳、專案名稱 100 字。
- **Claude 的建議：**依規格實作這些限制；專案名稱上限在前後端各寫一次，問我是否維持。
- **我的回應：**三者都要能調整，而且只改一處。
- **原因：**日後調整，或測試時需要改變數值。
- **結果：**數值集中在 `appsettings.json`（可用環境變數覆寫），程式與測試不寫死；新增一支唯讀 API，讓前端取得上限。

### 驗證時不使用 50MB 的檔案（2026-11-18）
- **Claude 的建議：**同步修改規格第 11.1 節，寫明單檔上限 50MB。
- **我的回應：**處理這一項時，把上限調小再驗證。
- **原因：**擔心 50MB 級的檔案讓 Docker 負載過高；上限本來就可以用設定指定。
- **結果：**規格註明 50MB 是預設值，手動驗證與自動化測試都以設定調小上限，不產生 50MB 級的檔案。

### 選到不合格檔案時的畫面行為（2026-11-19）
- **Claude 的建議：**問我要維持現狀，還是改成選到不合格的檔案時清掉先前選的檔案。
- **我的回應：**選到不合格的檔案時清掉檔案，自動帶入的專案名稱也一併清空；選到合格的檔案時，照原本行為帶入檔名。
- **原因：**我在瀏覽器實測時，先選超過上限的檔案、再選合格的檔案，專案名稱仍停留在不合格檔案的檔名。
- **結果：**依此修改並加上元件測試。

### 封存的任務與驗收條件衝突時怎麼辦（2026-11-19）
- **情境：**任務清單拆分後，規定子代理平常不讀已封存的任務。
- **Claude 的規劃：**只寫「不要讀封存檔，除非任務明確要求」。
- **我的回應：**提出這條規則沒有涵蓋例外：驗證時若遇到衝突、需要確認哪一邊優先，該怎麼處理。
- **結果：**共通約定新增「文件的優先順序與衝突處理」：子代理遇到衝突時停下來回報，由我決定，結果寫進 `decisions.md`。

### 不預先為上雲做調整（2026-11-19）
- **Claude 的建議：**把日後部署到 AWS／GCP 時要做的調整先記進文件，或現在就讓反向代理的信任網段可以設定。
- **我的回應：**兩者都不做。
- **原因：**上雲時我會再詢問，屆時依當下的環境評估，現在不預先設限。
- **結果：**階段七照原本的規劃進行。

### 反過來：我提出、經討論後沒有採用的做法
- **上傳改成非同步（2026-11-14）：**我認為同步解析要等很久，會影響使用體驗。Claude 說明改成非同步的代價（資料表要加狀態欄位、重複上傳無法再直接回 409、「先解析再存檔」的設計要改），建議先量測實際解析時間再決定。最後維持同步，前端在上傳中顯示處理狀態並停用按鈕。
- **用檔案雜湊判斷重複上傳（2026-11-17）：**Claude 說明同一模型重新匯出時，檔頭含匯出時間，雜湊會不同；以構件 GlobalId 判斷仍然必要。我原本想解決的情況（沒有可追蹤構件的模型可以重複上傳），改為直接拒絕這類模型。

## 紀錄與可追溯性

- 每個通過的任務單獨一個 commit（階段一～五由我提交，階段六起由 Claude Code 提交），commit 歷史與任務編號大致一一對應。
- `.claude/settings.json` 設定了 SessionEnd hook，對話結束時把 Claude Code 的原始對話紀錄（含子代理的派工內容與每個工具呼叫）複製封存，並轉成可閱讀的 HTML（自寫的 Python 腳本，只用標準函式庫）。封存內容含個人資料，不進 git。
- 封存保留的是行為（指令、工具輸入與輸出、回報），AI 的推理過程大多沒有以明文保存。

## 這套做法的限制

- 驗證者也是同一個模型，可能與實作者有相同的盲點；驗收條件寫得不完整時，驗證通過不代表沒有問題。我在 commit 前仍需自己讀 diff。
- 3D 檢視器沒有自動化測試，依賴人工確認。
- 詳細的任務與驗收條件讓流程較慢，對很小的修改來說成本偏高。
- 程式碼由 AI 撰寫，我對程式的理解來自規格制定、審查 diff 與處理衝突，而不是逐行手寫。
